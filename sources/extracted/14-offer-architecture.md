## Offer Architecture

Rempo go-to-market, Run 2. Skill phase: Phase 11 (added).

2026-10-19

Run 1's Phase 11 asked whether to lead with the done-for-you service or with software, and warned against running both as two companies. The founder has since answered: a hybrid, service-dominated, with the service as the front end and product upsells later in the same funnel. This phase sets how that works without turning into the two-company trap Run 1 described. Read with 09-pricing-packaging.md (prices) and 01-product-feature-matrix.md (what is held).


## Why the service leads

Run 1's comparison still holds, and it is why the founder's choice is sound:

For Rempo the service is what the evidence supports (Phase 0), what the competitors leave open (Phase 2), and what can be sold this month at a price that pays for advertising (Phase 9). The product layer is where margin can grow later, once the service has the customers.


## The ladder: one funnel, two layers

Every step reaches the same buyer through the same funnel: the same ads, the same VSL, the same onboarding call, the same 30-day review. Nothing in the product layer has its own trial, its own landing page, or its own ICP.


## The release rule: when a product item leaves "Hold"

The founder prefers not to add software features, to limit support. The rule makes that preference explicit and testable. A held item is released only when all five are true:

Asked for. At least two paying clients have asked for it without being prompted ({TBD}: the founder may set a different number).

Visible in their data. The account's own data shows the problem: missed calls for the receptionist, messages lost across apps for the inbox.

Delivered done-for-you. Rempo sets it up and tunes it; the client never configures software.

A support playbook exists before the first sale: the five most likely questions, answered, and a cap on support time per account per month ({TBD}).

Priced as an add-on to the service, not as a standalone software plan, so the buyer stays one customer with one relationship.

## Support load guardrail

Measured from the first add-on sale: support requests per account per month, by add-on, and founder and assistant minutes per request. An add-on whose support time exceeds the cap two months running goes back to "Hold" for new sales until its playbook is fixed.


## When to revisit

Triggers to watch, not dates:

Hours per account fall far enough that one assistant runs many more accounts: the service starts to scale like software.

Clients ask to run it themselves: a software-only plan may have a buyer.

Agencies ask to resell Rempo's program: the implementer route from Run 1 opens.

Each needs the time log by task (gtm-requirements-for-product.md), which is why it starts on day one.


### Table 1

| Dimension | Done-for-you service | SaaS |
| Start | Easy: revenue from the first client, on software that already exists | Hard: the product has to exist and win users first |
| Scale | Hard: each account adds labor | Easy: the next account costs little to serve |
| Sell | Easy: the buyer pays for work to be done | Hard: the buyer pays for a capability they must operate |
| Fulfill | Hard: the vendor does the work | Easy: the software does the work |
| Who does the work | The vendor | The client |
| Outcome certainty | High: the result does not depend on the buyer finding time | Lower: the result depends on the buyer using the tool |
